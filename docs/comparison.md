# 弈眼（Android）与桌面端 chessboard 实现对照

> 基准：桌面端 `chessboard`（Tauri + Rust，`server/src/`）vs 弈眼 Android
> （`app/src/main/java/com/yieye/xiangqi/`）。0.0.35 已完成识别层、状态机、引擎设置、
> 云库次优补充与熔断语义的对齐。0.0.36 起引擎时限/默认深度/云库超时按移动端硬件
> **有意偏离**（手机搜索速度到不了桌面级，参数值一致只会每步吃满时限；对齐的是
> "深度先到、提前收工"的行为模式而非数值），详见第二节各行标注与第七节。

## 一、总体架构

| | 桌面端 chessboard | 弈眼 Android 0.0.35 |
|---|---|---|
| 形态 | Tauri 桌面应用（Rust 后端 + Vue 前端） | Android Service（Java）+ 悬浮窗富文本 |
| 截屏 | xcap **拉式**窗口捕获（每拍必有画面） | VirtualDisplay+ImageReader **推式** + 最近帧缓存（等价改造） |
| 识别模型 | `large.onnx`，置信度 **0.7**，NMS 内嵌按类 LIMIT | `USE_YOLO_V11` 开关二选一：**0.0.35 起切回 `middle.onnx`**（与桌面 `large.onnx` 同文件，MD5 一致）+ YoloV5Detector（阈值 0.35）；备选 `yolov11.onnx`（与桌面旧构建模型同源），王类放宽 0.2 |
| 棋盘裁剪定位 | `start_listen` 时**一次性**缓存 `set_sub_bound`，窗口滚动/缩放后**不自愈** | `smartCrop` 缓存 + 连续 3 次识别失败清缓存重定位（**自愈**） |
| 方向模型 | `rotate.onnx` 可选编译（feature=rotate，未开源） | ❌ 按 r_jiang 位置推断方向 |
| 引擎 | Pikafish **独立进程**（UCI 管道），Threads=4 | Pikafish **JNI 进程内**，Threads=4 |
| 搜索 | `block_on(engine.search())` 阻塞，单搜索在飞 | `EngineHelper.searchSync` latch 阻塞，单搜索在飞 |
| 引擎生命周期 | 应用级单例（`OnceLock`），不随监听重建 | **进程级单例**（0.0.18 修复回调错位），跨会话复用 |
| 容错自愈 | 无 | 心跳看门狗 30s：dump 堆栈 + 重建检测器 + 换线程 |
| 循环节拍 | 200ms（config 可调） | 300ms（含截屏+哈希开销） |
| 云库 | chessdb querypv+queryall（5s 超时）；NotResult 与 ServerInternalError 状态分得清、处理相同 | 同协议；0.0.35 起 `STATE_SERVER_ERROR` 与"库中无此局面"分离，**仅连续 2 次网络不可达才熔断 5 分钟**；0.0.36 起超时 2s（慢网早落本地引擎） |

## 三、同一功能的不同实现细节

1. **走子方推断**：两边都取"消失格棋子"定走子方（桌面 `Changed.camp`，Android
   `cmp.movedChess` 前缀）。Android 额外处理合并帧（两步并一帧 → 子数不变则行棋方
   不变）与幻影帧拦截。注意桌面对"两格变化但只有单侧（双消失/双出现）"判为 One，
   Android 判为噪声跳过——效果等价。
2. **单格变化恢复策略**（最大行为差异）：桌面 One → 计数 3 次回 Initial 全量重锚定；
   Android 噪声跳过 + pHash 回滚让下一拍重试同一画面，连续 8 拍才按底部方兜底出招。
   根因是识别域不同：桌面 0.7 阈值下几乎不出坏帧，重锚定安全；手机高亮/动画下
   坏帧连片，重锚定会把坏帧当基线。
3. **棋盘归一化**：桌面 `detections_to_board` 按王位置定阵营 → `board_fix` 旋转数组
   统一红在下；Android 解析时按 `r_jiang` 的 yPos 直接输出标准方向 FEN，
   `fenToBoard(bottomIsRed)` 再旋转——等价实现。
4. **评估颜色语义不同**：桌面 `formatEval` 颜色按**我方利益**（mirror 事件推我方阵营，
   红=利好我方，绿=利好对方），标题带"我方/对方"归属；Android 悬浮窗按**行棋方视角**
   固定着色（优绿/劣红），不带阵营归属。文本翻译（杀步/均势/四档）两边一致。
5. **中文记谱**：两套独立实现，主干（前/后/平进退、士象马终点、纵线）一致。差异：
   - 黑方纵线数字桌面用半角 `1-9`，Android 用全角 `１-９`；
   - **多列兵重叠数子**桌面有完整实现（`overlap_piece_xy` 跨列编码排序取序，
     支持"前中后/一二三"全场景），Android 对 3 兵以上场景简化为 `intToChina(front+1)`，
     极端局面记谱不规范；
   - 桌面 red 帅/士/象的进退终点用 `verticals[8]` 技巧位，输出形式与 Android 的
     标准目标纵线写法略不同（均属常见记谱变体）。
6. **云库状态语义**：桌面 `NotResult`（库中无此局面）与 `ServerInternalError`（网络错）
   分得清但处理相同（都落引擎）；Android 0.0.35 起状态模型同构（`STATE_UNKNOWN` /
   `STATE_SERVER_ERROR`），且额外用网络错计数做 5 分钟熔断。
7. **截屏域差异**：桌面拉式（每拍必有画面）+ 裁剪区启动时一次缓存；Android 推式 +
   最近帧缓存（静止期饥饿补偿）+ pHash 去重（功耗优）+ 裁剪失效自愈重定位。
8. **引擎通道**：桌面 UCI 子进程管道；Android JNI 进程内 + CountDownLatch 阻塞。
   均保证"任何时刻最多一个在途搜索"。Android 因 native 回调全局注册，
   引擎必须跨会话单例复用。
9. **启动语义**：桌面 `start_listen` 首帧识别不到棋盘直接报错返回，需用户重试；
   Android 进入 INITIAL 持续重试直到锚定成功（悬浮窗显示"等待识别"）。
10. **mate 分数编码**：两边一致（±(30000−步数)），候选取舍与"形势"翻译共用同一公式。
11. **配置**：桌面 config.json 全量可热改；Android 为编译期常量 + 深度选择器
    （运行中改深度不生效，需重启服务）+ 王位记忆持久化。

## 四、Android 多出的机制（移动端补偿）

- 心跳看门狗（ONNX 推理挂死 30s 自愈：dump 堆栈 + 重建检测器 + 换线程）
- 截屏最近帧缓存（推式截屏的静止期饥饿补偿）+ 裁剪缓存失效自愈
- 丢王一致性修复 + 跨会话王位记忆 + 低置信王九宫补位
- 幻影/半步/不成对帧的显式拦截、修复帧守卫与 pHash 回滚
- pHash 去重、悬浮窗富文本（ponder/相对分数/耗时/来源）、出招先验货、
  INITIAL 合法性门槛
- 云库熔断（仅网络不可达计数）

## 五、Android 尚缺 / 可选跟进

- 完整棋盘镜像 UI 与着法列表（当前仅悬浮窗文本）
- config.json 式可配置化（循环节拍/门槛/云库开关为编译期常量）
- 中文记谱多列兵重叠的完整实现（桌面 `overlap_piece_xy` 方案，可移植）
- JVM 单元测试（FEN/记谱/协议解析均为纯函数，桌面 chess.rs 有可对照的测试）
- rotate.onnx 方向模型（桌面可选编译，未开源但本机有文件，可评估移植）
- GPU/其他执行提供（Android 为 CPU EP）
- 残局挑战装饰环的模型微调（识别根治方案）

## 六、已知边界（两端共有）

- 复盘/浏览历史局面时"轮到谁"画面上不存在：按屏幕底部方启发式猜测，
  走一步后自动纠正；
- 识别置信度受 UI 特效（高亮/动画）影响：两端都以"确认 + 分类门槛"抵御，
  Android 另有噪声帧跳过与王位记忆兜底。

## 七、引擎参数设置依据与两端配置对照（0.0.36）

### 两端配置逐项对照

0.0.35 及之前 Android 与桌面端参数值完全一致（0.0.22/0.0.23/0.0.35 多次迁移刻意对齐）；
0.0.36 起 4 项按移动端硬件有意偏离。逐项核对如下
（桌面端基准：`engine/mod.rs` `EngineConfig::default`、`config.rs:32-33`、`chessdb.rs`、`worker.rs`）：

| 参数 | 桌面端默认 | Android ≤0.0.35 | Android 0.0.36 起 |
|---|---|---|---|
| 默认搜索深度 depth | 20 | 20 | **16**（UI 仍可调 6~30 偶数档） |
| 每步思考上限 time | 5000ms | 5000ms | **2000ms**（`ENGINE_STEP_TIME_SEC`） |
| 云库超时 | 5s/请求（reqwest 整体超时） | connect 5s + read 5s | **connect 2s + read 2s** |
| 云库缺次优的本地补搜 | 全额 depth/time（mod.rs:267） | 全额 depth/time | **1s 短搜**（`SUPPLEMENT_SEARCH_TIME_SEC`，最优仍以云库为准） |
| Threads / Hash | 4 / 64 | 4 / 64 | 4 / 64（不变） |
| MultiPV / alt_score_gap | 3 / 300 | 3 / 300 | 3 / 300（不变） |
| Sixty Move Rule / Slow Mover | false / 不设置 | 同 | 同（不变） |
| UCI_ShowWDL | true（默认） | 不设置（=false） | 不设置（不变）；纯输出开关，不影响搜索。此前 Android 注释误写"桌面为 false"，已更正 |
| 循环节拍 | 200ms（config 可调） | 300ms | 300ms（不变） |
| confirm 确认 | 睡 100ms 复抓，失败再睡 confirm_interval(200ms) | 固定睡 200ms 复抓一次 | 不变 |

### 为什么"参数一致"手机仍然慢（0.0.35 的困惑）

`go depth 20 movetime 5000` 是双上限、谁先到谁停：**深度是质量下限**（想到即提前收工），
**时间是耐心上限**（到点必须交卷）。同一个配置在两端触发的根本不是同一个上限：

- 桌面 CPU 4 线程搜索速度快，常在 1~3s 内**提前到达 depth 20** 自行停止——时间上限很少
  生效，实际每步只搜 1~3s；
- 手机 4 线程速度只有桌面几分之一（持续搜索还会热降频），**5s 烧完也到不了 20 层**——
  每步都吃满 5000ms，深度上限形同虚设。

引擎之外每一段也都更慢：YOLO 只能走 CPU（桌面另有 CUDA/DirectML），且手机每步要识别
3 次（识别 + confirm 复抓 + 出招验货帧），加上循环 300ms 与 confirm 固定 200ms。
合计桌面端每步约 2~4s、手机端约 6.5~8.5s——本质是"对齐了参数值，错位了硬件"。

### 0.0.36 各参数取值依据

| 调整 | 依据 | 代价 |
|---|---|---|
| movetime 5000→2000ms | 手机在 5000ms 内到不了 20 层，差额只是白等；2s 约可到 15~17 层（估算，因机型而异） | 棋力略降（约浅 2~4 层），复杂对攻局面偶尔推荐差一档的招 |
| 默认深度 20→16 | 让"深度先到、提前收工"重新成立：简单局面/残局约 0.5~1s 返回；复杂局面反正被 2s 时间上限卡住，与 20 结果相同。16 层 NNUE 已远超人类水平，做参考绰绰有余 | 简单局面少等的那零点几秒换来的几层深度，对参考价值微乎其微 |
| 云库超时 5→2s | chessdb 正常 RTT 数十~300ms，2s 已覆盖"慢而通"；更久说明网络差，该落本地引擎而非白等 | 持续慢网会频繁超时（计 SERVER_ERROR→两次即熔断 5 分钟），等于长期不用云库；换来单步延迟上限可控 |
| 补搜全额→1s | 该搜索只为凑"备选"展示，最优招/评分/深度均以云库为准；1s × MultiPV=3 约 12~14 层，够参考 | 备选招法可靠性略降、可能凑不满 2 个 |

预期出招延迟：云库命中约 1.5~2.5s，未命中约 2.5~3.5s，最坏约 4s。
若实测觉得棋力不足，两个回调旋钮：主界面深度调回 18，或 `ENGINE_STEP_TIME_SEC` 调到 3.0
（每 +0.5s 约换 1 层深度）。
